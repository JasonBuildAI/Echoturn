# 基准

**English: [benchmarks.md](benchmarks.md)** —— 英文版是唯一真源，本页是它的中文对照。
两版不一致时以英文版为准；改英文版时要同一个 commit 改这一页。

一个脚本，一个问题：**一轮的延迟里，有多少是这个库自己的责任？** 脚本是
[`bench/latency.py`](../bench/latency.py)，它到底量什么、不量什么，以它的模块 docstring
为准。这一页讲的是怎么读它的输出。

```bash
pip install -e ".[dev]"
python bench/latency.py                              # 发布时的攒句策略
python bench/latency.py --compare                     # ……与一个「等整段」的策略对比
python bench/latency.py --token-ms 25 --compare        # 在一个值得比较的模型节奏下
python bench/latency.py --json                         # 喂给别的东西
```

不联网、不要 Key、不下模型：用的是离线供应商，所以关掉 wifi 跑出来的数是一样的。

## 各列的含义

| 列 | 从哪一刻起算 | 什么会让它变 |
|---|---|---|
| `first token` | 这一轮开始 | 走到一个 `sink` 事件并拼好提示词的时间，再加上模型产出第一个片段之前做的事 |
| `first audio` | 这一轮开始 | 上面全部，再加上第一片在「值得提交」之前等了多久 |
| `total` | 这一轮开始 | 上面全部，再加上剩下的每一片，以及最后一句的合成 |
| `chunks` | —— | 攒句策略：这条回复被切成了几次合成调用 |

每一格是若干次运行的中位数（p95），单位毫秒。要引用的是中位数；p95 放在那里，是为了让「平时
都很好、偶尔极差」的策略不至于和「一直很好」看起来一样。

## 要比较策略，`--token-ms` 就不是可选项

离线模型是瞬间吐出整个答案的。这很方便，也很误导：模型是瞬间的，「等整段」什么代价都不用付，
于是发布策略和一个从不提前冲刷的策略量出来一样。`--token-ms` 在模型每个片段前加一段睡眠，
这时比较才有意义 —— 提前冲刷把「模型还在写的那段时间」从首声延迟里去掉，而这正是两行的差别。

节奏会印在每一行旁边。一个没有标明「是在什么模型节奏下取的」延迟数字，什么都不能说明。

## 这些数字不是什么

- **不是预测。** 一个到首 token 要 800 ms 的托管模型，会给每一行都加上 800 ms。这个库不可能
  知道那件事，它的基准也不可能。
- **不是 TTS 延迟。** 离线语音是用 Python 合成的一声蜂鸣：那是真实的 CPU 开销，快慢方向和
  托管语音一致，但幅度不同。要比就拿行和行比。
- **不是你的机器。** 在你部署的地方跑它。这里真正有意思的，通常是差别的方向和大小，而不是
  绝对值。

## 加一个基准

两条规矩，和这个仓库别处一样：量一件读者**能据此行动**的事，并把取这个数时的条件印出来。
一个没有带上条件的数字会被引用五次，然后变成错的。
