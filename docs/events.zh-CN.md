# 事件

**English: [events.md](events.md)** —— 英文版是唯一真源，本页是它的中文对照。
两版不一致时以英文版为准；改英文版时要同一个 commit 改这一页。

一轮就是一条普通字典组成的流。做成流而不是回调式 API，是因为消费方几乎总是「得把它们
送到别处去」的东西 —— 一个 SSE 响应、一个 websocket、一个队列；也因为一轮同时在做的三件
事，只有流这个形状扛得住。

造这些事件的是 `echoturn.events`，名单在 `EVENT_TYPES`。

## 七个事件

| 事件 | 字段 | 含义 |
|---|---|---|
| `ack` | `id` | 这条消息已落定，就是这个 id |
| `sink` | `audio_sink`、`notice` | 声音从哪里出来 |
| `sentence` | `i`、`text` | 第 `i` 条消息里的一句可朗读的话 |
| `audio` | `idx`、`i`、`mime`、`data` | 一片 WAV（base64），位置是 `idx` |
| `aborted` | `reason` | 这一轮被停了。终局 |
| `done` | `reply`、`timings`、`warnings`、`extra` | 这一轮完成。终局 |
| `error` | `error` | 这一轮失败。终局 |

`aborted`、`done` 与 `error` 就是 `echoturn.events.TERMINAL`：正好其中一个结束一条流，
它后面不会再有东西。做成三种结束而不是一种，是因为「她说完了」「我们把她停了」和
「它坏了」在屏幕上需要不同的话，不该靠「回复是空的」去猜。

### `ack`

在任何花销之前、在任何慢操作之前发出。它让客户端能区分「根本没送到」和「送到了，然后被
打断」—— 没有它，两者看起来都像一次失败的请求，于是用户把一条已经收到的消息重打一遍。

宿主给了 `TurnInput.message_id` 时 `id` 就是它，没给就是一串生成的十六进制。

### `sink`

永远第二个发出。它存在的意义是：决定声音从哪里出来这件事不能拖慢回复。把音频路由到别处
（手机、队列、文件）的宿主在这里回答，而不是在合成里回答。`notice` 原样展示给人看；
发布版本里的值是空的。

今天这个包只会发出一个值 `"browser"`，因为它只带了 `clients/` 这一个客户端。这个事件不是
占位符：换掉它就是宿主改变答案的方式。

### `sentence`

字幕流，而且它比音频先到。`i` 是这句属于本轮的第几条消息。

这里流过去的是**每一次合成请求的文本**，不是回复拆出来的句子。两者不是一回事：一片是按
字符预算切出来的，里面可能装了两句短句；把 `sentence` 事件接回去也拼不出 `done.reply`。
`done.reply` 才是说出口的东西。

写给程序读的东西永远不会被念出来。围栏代码块和 JSON 对象在到达合成之前、也在到达气泡之前就
被摘掉；只有**真的解析得成对象**的才摘，而一行以 `{` 开头又始终没有闭合的，按半个契约丢掉。
散文里的花括号一个字都不动。所以一整轮只有对象时不会发出任何 `sentence` 与 `audio`，而
`done.reply` 里仍然留着那个对象 —— 要结构化输出的宿主读得到它，而嗓子念不出来。

### `audio`

一片 base64 的 WAV，`idx` 是它在本轮中的位置。

**`idx` 是排序键，不是提示。** 片是并行合成的，完成顺序天然是乱的；照着到达顺序播放的
客户端会把两句话穿插着播。**每片都要等到它前面所有片都播完再播。**

用 WAV 而不是裸采样，是因为浏览器不用被告知采样率、声道数和编码就能解码 —— 这三样正是
语音供应商可以随便选的，也正是靠猜的客户端会**悄悄**搞错的三样。

`i` 是这一片属于哪条消息。一条长回复可能有好几条。

### `aborted`

`reason` 是个短词，给客户端挑措辞用。这个包发出的那个是 `"superseded"`：更新的一轮顶掉了
这一轮，或者客户端断开了 —— 调用方分不清这两者，也不需要分清。

被打断的一轮通常已经发出过一些 `audio`。那些音频是**真的说出口了**，所以会给对话留档的
宿主应该写「实际说出去的内容」，而不是什么都不写。

### `done`

| 键 | 里面是什么 |
|---|---|
| `reply` | 整条回复，清洗过的文本 |
| `timings.first_token_ms` | 模型第一个片段到达的时刻 |
| `timings.first_audio_ms` | 第一片可以播的时刻 |
| `timings.total_ms` | 整轮 |
| `timings.chunks` | 一共提交了几片 |
| `warnings` | 做得不好的部分，首先是某一片没能念出来 |
| `extra.input_kind` | 宿主给这一轮打的标签 |

`warnings` 不是放「把这一轮搞坏的事」的地方 —— 那些是 `error` 事件。它放的是某一片语音
合成失败：文本还在 `reply` 里、还读得到，而调用方有资格知道那句话从没被念出来。
格式是 `"chunk 3: ProviderError"`。

`first_token_ms` 与 `first_audio_ms` 在**没发生过**时是 `None` —— 对一轮纯文字来说，
这才是诚实的答案。

### `error`

`error` 可以放心摆到人面前。异常原文不行，它属于宿主的日志：里面带着 URL、密钥和内部路径。
决定一条消息属于哪种的是 `echoturn.errors.safe_message`。

## 顺序

保证：

* `ack`，然后 `sink`，然后才是别的；
* `sentence` 与 `audio` 自由交错（字幕先于声音，这是设计）；
* `audio` 事件按 `idx` 顺序发出，不管它们是按什么顺序完成的；
* 终局事件正好一个，在最后；
* 终局事件之后什么都没有。

不保证：

* `sentence` 与 `audio` 交替出现；
* `audio` 里的 `i` 单调递增（属于第 0 条消息的一片可以晚于属于第 1 条的一片发出）。

## 线上格式

`echoturn.events.encode` 每个事件写一帧，一字不差：

```
data: {"type":"sentence","i":0,"text":"Hello there."}\n\n
```

文本不转义成 ASCII。从这里到浏览器之间的每一跳都是 UTF-8，而 `\uXXXX` 转义会让一条中文
回复的体积涨到三倍，换不来任何**看得见**的好处。

`echoturn.integrations.starlette.sse_response` 就是整座桥：一个同步生成器在自己的线程上，
推进一个 asyncio 队列，带上 `Cache-Control: no-cache`、`Connection: keep-alive` 和
`X-Accel-Buffering: no` —— 最后这个正是用来防止某个代理把一条流变成「最后一次性到齐」的
回复。

## 从 JavaScript 读它

解析这些帧的是 `clients/stream.js`。其中一条规矩值得在这里重复：

```js
const { events, rest } = splitFrames(carry);
```

分块的边界不会照顾帧的边界 —— 一次读可以停在一个 JSON 对象的中间 —— 所以尾巴要留到下一次
读，只有完整的帧才拿去解析。一帧里读不出东西只会被计数，不会抛出去：丢一句不等于丢一条
回复。
